A docs platform that can’t quietly go stale

Research and a recommended build for a single documentation site covering both halves of City Scrapers — the Meetings Viewer, and the scraper building & QA guide — that your team edits continuously and CI keeps honest. Everything below is free and open source.

Recommendation

Build it inside the app

Mount Fumadocs 16 at /docs inside the existing Next.js app, with MDX content in content/docs/, Keystatic at /keystatic for teammates who won’t touch a terminal, and a CI layer that lints prose, checks links, and flags docs whose underlying code has moved. One repo, one deploy, one design system, a preview URL on every docs PR.

The deciding fact: Fumadocs is the only current option that can live inside a Next.js 16 App Router app. Docusaurus, Starlight, and VitePress are standalone site generators — adopting one means a second deployment and a second visual identity. Nextra could mount at a subpath in principle, but it is broken on Next.js 16.2.5+ with an open, unanswered issue and no release since December 2025.

01 What this actually has to solve

CS-121 asks for one documentation page covering two things that look related but aren’t: how to use and develop the Meetings Viewer, and how to build and QA a scraper. Those have different readers, different lifespans, and different failure modes. Worth being explicit about them before picking tools.

Reader A — the apprentice

“I’ve been assigned a city. Now what?”

Needs a path, not a reference: analyse the source, pick a spider pattern, write the parse method, get output into the viewer, check it against the rubric, open a PR. Reads sequentially, once, under pressure. Most of what they need is currently in a Google Doc they have to alt-tab away from their editor to read.

Reader B — the reviewer

“Is this scraper actually correct?”

Needs a rubric they can apply field by field against real output, fast, without re-deriving it from memory. This is the same job the Meetings Viewer exists to speed up — which means the docs and the app are solving one problem, and should live together.

The three failure modes to design against

  • Drift. The rubric says end defaults to start + 2 hours. If that changes upstream and nobody edits the doc, the doc becomes actively harmful — worse than no doc, because people trust it. Every mechanism in §7 exists for this.
  • Contribution friction. Documentation that only one person can update becomes that person’s backlog. If a mentor spots an error in the QA rubric, fixing it should take two minutes and no local setup.
  • Two sources of truth. Today the schema table exists in a Google Doc, in README.md, and implicitly in the app’s TypeScript types. Three copies, guaranteed to diverge. The plan is one canonical source per fact, with the rest generated.
Why not just keep the Google Docs

They’re genuinely fine for drafting, and the two you have are well written. What they can’t do: be reviewed alongside the code change that made them wrong, be linked from an error message, be searched with ⌘K next to the thing being described, render a live component, or be checked by CI. Keep Google Docs for drafting; make the site the published artifact.

The one real cost of Fumadocs

fumadocs-ui@16.15.1 and fumadocs-core@16.15.1 both declare "next": "16.x.x" — a single-major range. It is not quite a wall: every Fumadocs peer is marked optional in peerDependenciesMeta, so npm warns rather than refuses, and an overrides entry would force it. But a strict resolver or CI running --strict-peer-deps will fail, so treat it as a real coupling: pin both versions, upgrade them as one unit, and note it in AGENTS.md. Fumadocs releases near-daily, so the lag should be short.

If you’d rather not couple docs to the app at all

The honest alternative is Starlight deployed separately, proxied in via next.config rewrites at /docs/:path*. You get complete isolation — no CSS conflict, no version coupling, docs can’t break the app build. You lose the shared header, the shared theme, a shared search, and the ability to render live app components in a doc page. Given that §5 is largely built on that last capability, the coupling is worth paying for. But if the team’s priority is that the viewer never breaks because of a docs dependency, this is the defensible second choice.

03 Fitting it into the app you already have

The app is already set up for this. The CSS layer order is declared, MUI runs on CSS variables with a data-attribute colour scheme, and shared logic sits in a top-level lib/. Routes are split into (app) and (landing) route groups; adding (docs) is the same move a third time.

Why the CSS cascade is already safe

globals.css declares the layer order explicitly, which is what makes Fumadocs safe to add: 

@layer theme, base, mui, components, utilities;
@import "tailwindcss";
@import "fumadocs-ui/css/neutral.css";
@import "fumadocs-ui/css/preset.css";

Fumadocs’ preset emits exactly two global rules, both in @layer base — a universal border-color, and body { background-color: var(--color-fd-background) }. With mui ranked after base, <CssBaseline /> wins on body app-wide, while Fumadocs still colours its own containers inside /docs. Had the order been left undeclared, mui’s rank would depend on when Emotion injected its style tag, and the app background could repaint to the docs theme.

One consequence worth knowing: components and utilities outrank mui. Inside /docs that is what you want — Fumadocs’ prose styles should beat MUI defaults there. Outside /docs none of those classes apply, so nothing changes.

And why the palette is already shareable

app/theme.ts runs createTheme({ cssVariables: { colorSchemeSelector: "data" }, colorSchemes: { light: true, dark: true } }), with <InitColorSchemeScript attribute="data" /> in the root layout to prevent a flash of unstyled content.

That matters more for CS-121 than it does for the app: MUI emits real --mui-palette-* custom properties, which is the precondition for theming Fumadocs from your palette instead of maintaining a second one. §8 builds on it.

Do not import fumadocs-ui/style.css

That prebuilt file is a fully compiled Tailwind bundle including a complete Preflight and unprefixed :root theme tokens. It exists for apps with no Tailwind of their own and will clobber yours. Always use the neutral.css + preset.css source path shown above.

Note

Next.js allows exactly one root proxy.ts (the renamed middleware.ts). You have none today, so Fumadocs’ content-negotiation file is free to add — but if you later add auth middleware, the two must be merged rather than coexisting. Worth a comment in the file.

Node.js version — no conflict

The repo declares engines: { "node": ">=20.9.0" }, which is Next.js 16’s own minimum. Fumadocs adds no constraint: neither fumadocs-ui@16.15.1 nor fumadocs-core@16.15.1 declares an engines field, and the manual-installation page lists only Next.js 16 and Tailwind CSS 4 as prerequisites. Some write-ups claim Fumadocs needs Node 22 — that figure comes from the create-fumadocs-app scaffold, not the libraries. Confirm during the P0 spike anyway, since npm won’t warn either way when no engines field exists.

04 How content reaches a page

Three different kinds of author write into the same folder, and one build pipeline serves all of them. That’s the whole architecture — and it’s why the visual editor and the generators don’t need any special support from the framework.

05 The UX layer — what makes this better than a wiki

Everything so far is plumbing. This is the part that decides whether people use it. The through-line: the docs should do work, not just describe it. Ten concrete things, roughly in order of value per unit of effort.

1. Paste your scraper output, get a rubric report

The highest-value page on the site. A drop zone on the QA page: paste or drop a scrapy crawl -O JSON file and get a per-field verdict against the rubric in §2.5 of the development guide — timezone-aware datetimes, titles containing a date, empty location with no time_notes, links out of priority order, status inconsistent with start, duplicate IDs. Runs entirely client-side; nothing is uploaded.

This is the same job the Meetings Viewer already exists to do, so most of the logic is a lift from lib/meetings.ts and lib/duplicates.ts — both top-level and cleanly importable from a docs route.

2. Docs that render the real components

Because /docs lives in the app, an MDX page can do this: 

import { StatusChip } from '@/components/ui/StatusChip'

<!-- this legend is the component, not a screenshot of it -->
<StatusChip status="cancelled" /> — the source explicitly says so.

Status legends, location formatting, link ordering, the duplicate badge: all documented by rendering the real thing. Those pages are structurally incapable of drifting. Do this everywhere it applies before reaching for any drift-detection tooling.

3. An interactive rubric explorer

The twelve-field schema table is the single most-consulted artifact in the whole project, and a wide table is a poor container for it. Make it a component: choose a field, get expected behaviour, edge cases, a good/bad example pair, and the spider code that produces it. Deep-linkable — /docs/qa/schema#links — so a reviewer can drop the exact anchor into a PR comment instead of retyping the rule.

4. Command blocks that know your spider

One input at the top of the “running a spider” page — spider name, path to the viewer — and every snippet on the page fills itself in, with a copy button. This kills the two most common apprentice errors in one move: lowercase -o instead of -O (which silently appends and duplicates records), and writing to the wrong data/scrapers/ path.

5. A QA checklist that exports to the PR

The pre-submit checklist as real checkboxes, state kept in localStorage, with a Copy as PR comment button that emits a markdown checklist. Docs feed the review workflow rather than sitting beside it. Pair with your existing .github/PULL_REQUEST_TEMPLATE.md.

6. Two front doors, not one

The /docs index should be two paths, not a wall of links: “I’m building a scraper” and “I’m reviewing one.” The two readers in §1 need almost disjoint pages; making them choose in the first three seconds is worth more than any amount of sidebar organisation.

7. Diagrams in the content, not in a Figma nobody opens

Mermaid, registered as an MDX component. The obvious first three: local vs production data flow; the PR data lifecycle across run-and-save.yml and cleanup-data.yml; and the decision tree for singular spider vs spider factory. Fumadocs ships no Mermaid wrapper, so this is a small client component using mermaid with the theme wired to the current colour scheme — roughly 30 lines.

8. Callouts that match the guide you already wrote

The development guide already uses TIP NOTE CAUTION. Fumadocs’ <Callout> maps onto those one-to-one, so the migration is close to mechanical and the voice carries over intact.

9. Copy as markdown, and an llms.txt

Fumadocs generates /llms.txt, /llms-full.txt, per-page .md routes, and a copy-as-markdown button out of the box. For a cohort of apprentices working across time zones, being able to paste an exact doc page into an AI assistant at 11pm is a genuine support channel, not a novelty. The llms.txt spec reached v2 in August 2026 and Chrome’s Lighthouse now audits for it.

10. Search that’s actually reachable

⌘K from anywhere, including from inside the viewer itself. Fumadocs’ default engine runs in your own Next.js process — no external service, no key, no quota.

Sequencing

Items 2, 7 and 8 come nearly free with the framework and should land in the first migration. Items 1, 3, 4 and 5 are real feature work — roughly one sprint together — and are what turn this from “we moved the Google Doc” into something the team would miss if it disappeared. Don’t start them until the content migration has shipped.

06 Editing without touching git

You said mentors and PMs need a visual editor. That constraint eliminates most of the field, because the intersection of free, MDX with custom components, git-backed, and Next.js App Router is small.

One boundary to set first, because it is easy to misread: reading /docs is anonymous and stays that way. Authentication applies only to the write path, and it is unavoidable there — content lives in a git repo, so every change is a commit and every commit needs an author. There is no anonymous-write option worth building: it would mean either a bot token committing on behalf of unauthenticated visitors (an open write endpoint into the repo) or a database, which breaks the viewer’s no-database invariant. Attributable commits in reviewable PRs are what make CODEOWNERS and everything in §7 work at all.

Sveltia CMS MIT Markdown only No Yes Wrong format

What the free path actually involves

Less than people expect. Keystatic’s GitHub mode is a one-time setup, not a service you run:

  • Create a GitHub App through Keystatic’s own guided flow and grant it access to the repo.
  • Put KEYSTATIC_GITHUB_CLIENT_ID and KEYSTATIC_GITHUB_CLIENT_SECRET in the Vercel project’s environment variables.
  • Editors visit /keystatic and sign in with GitHub.

There is no user database, no session store, and no permission logic for us to write or secure. GitHub enforces access, not our code — the admin UI unlocks for accounts with write on the repo and does nothing for anyone else. The only secret we hold is the App’s client secret.

Note that /keystatic is a public route in the app. That is not a hole — an unauthorised visitor gets a sign-in screen and GitHub rejects the write regardless — but if we would rather the editor exist only in preview deploys, Keystatic publishes a recipe for it (“Next.js: Disable Admin UI Routes in Production”).

The decision nobody can make for you

Keystatic’s self-hosted GitHub mode is fully free and mounts inside your app — but every editor needs a GitHub account with write access to the repo. Keystatic Cloud exists precisely to remove that requirement: free for 3 users, then $10/month per team plus $5 per extra seat.

For an apprenticeship programme this may be a non-issue — mentors and apprentices already have GitHub accounts, and giving mentors write access to a public docs repo is normal. Confirm that before assuming a paid tier is needed. If more than three genuinely non-technical people need to edit, TinaCMS Cloud is the alternative, but note its free tier is 2 users, which is effectively unusable, and self-hosting Tina means running a database.

Verify before committing

@keystatic/next@5.0.5 declares next: ">=14" and react: "^18.2.0 || ^19.0.0", so your Next 16 / React 19.2 stack satisfies the peer range. But the install docs still say “assumes an existing Next.js 14 project,” and the Next adapter sat unreleased from Feb 2025 to Aug 2026. Spike it on a branch for half a day before it goes in a ticket. Also: meta.json sidebar ordering has no natural Keystatic representation and will probably stay a developer task.

Two things the Keystatic docs do not answer, both of which change the governance story and should be settled in the same spike:

  • Does an edit commit straight to the branch, or open a pull request? There is no branching or pull-request page in Keystatic’s documentation. Whether a mentor’s edit lands directly or goes through review is not a detail — find out by trying it.
  • How does Keystatic Cloud attribute commits? Undocumented. If history shows a generic Keystatic identity rather than the individual editor, that undercuts CODEOWNERS-based review routing and is an argument against the paid path independent of cost.

The zero-setup fallback, if the access question stalls, is github.dev: a contributor forks the repo, edits MDX in a full browser editor, and opens a PR. That needs only a free GitHub account and no repo permission at all — write access is required only for committing directly. What you give up is the WYSIWYG and schema validation; what you keep is the review loop, and a Vercel preview per PR covers the “can I see it rendered” problem better than any CMS preview pane.

Two constraints of Keystatic’s MDX field are worth knowing up front, and both happen to suit Fumadocs: no import statements inside MDX files, and no raw HTML tags. Fumadocs injects its components globally through getMDXComponents() rather than per-file imports, so pages authored through Keystatic can still use <Callout>, <Tabs> and <Steps>. The pages that do import live app components (§5 item 2) become developer-owned — a reasonable split.

07 Keeping it true

Continuous updating is the requirement that actually distinguishes this from “a nicer Google Doc.” Four independent mechanisms, weakest guarantee to strongest.

The CI pipeline

Adoption order matters more than tool choice here. The single most common way a docs pipeline dies is being red on day one, so every gate below is sequenced to start green.

Step Tool Runs On failure Effort
1. Review routing CODEOWNERS path globs Every PR Requests a docs reviewer 1 file
2. Spelling cspell-action@v8, incremental_files_only Every PR Inline annotation 1 hour
3. Markdown lint markdownlint-cli2 on .md; remark-lint on .mdx Every PR Annotation 2 hours
4. Internal links lychee --offline --include-fragments Every PR Blocks merge 1 hour
5. External links lychee-action@v2, cached Nightly Opens one rollup issue 1 hour
6. Prose style vale-cli/vale-action@v3 + Google + MDX packages Every PR Inline review comments on the diff only ½ day
7. Accessibility @axe-core/playwright Every PR Blocks merge — zero violations ½ day
8. Perf / SEO lighthouse-ci-action@v12, runs: 3 Every PR Warning only 2 hours
9. Generated pages Custom script + git diff --exit-code Every PR Blocks merge 1 day
10. Freshness last_reviewed + ttl_days frontmatter Weekly Rollup issue, assigned by owner ½ day
11. Code drift Fiberplane Drift anchors Every PR Fails on anchored pages only Pilot
Vale moved orgs

Nearly every tutorial you’ll find says errata-ai/vale-action@v2. Vale is now vale-cli/* — use vale-cli/vale-action@v3, and add Packages = MDX, Google pinned to release URLs so an upstream rule change can’t break an unrelated PR. Put your project jargon (Scrapy, LegistarSpider, Legistar, spider prefixes like sandie) in styles/config/vocabularies/CityScrapers/accept.txt — entries are case-sensitive regexes, not literals.

Generated, not written

Three pages should never be hand-edited:

  • The meeting record schema table — generated from the app’s TypeScript types. It currently exists in three places (Google Doc, README, code); pick the code as canonical and generate the rest.
  • The command reference — generated by introspecting the Scrapy command classes rather than transcribed. Scrapy’s CLI is argparse-based, so sphinx-click and mkdocs-click don’t apply; a short script that walks the command classes does.
  • The spider registry — generated from the manifest, once production mode exists.

The rule that makes generation worth doing: a generated file must be either gitignored and built at deploy, or committed with a CI check that regenerating produces no diff. A committed generated file with no such check is worse than no generation at all, because it looks authoritative.

Freshness, done so it isn’t gamed

---
title: Writing a Legistar spider
last_reviewed: 2026-06-01
ttl_days: 180
owners: ['@ctd/scrapers']
---

Warn at 1× TTL, fail at 2×, never on the PR itself — a weekly job opens one rollup issue assigned via owners. Failing a PR on a date is how these systems get disabled: people bump the date without reading the page, and you have built a metric that lies. Vercel’s own docs serve exactly this kind of frontmatter and are a good schema to copy.

08 Making it look like one product

The real aesthetic risk of mounting Fumadocs inside an MUI app is a visible seam — docs that look like a different website reached through your header. It’s avoidable, and cheaply.

Fumadocs’ entire theme is a set of --color-fd-* custom properties, all namespaced, none of which collide with your tokens. So you don’t theme Fumadocs by overriding its components — you map its variables onto your MUI palette once, in globals.css: 

/* one place, ~20 lines, and it handles BOTH themes automatically */
:root {
  --color-fd-primary:    var(--mui-palette-primary-main);
  --color-fd-background: var(--mui-palette-background-default);
  --color-fd-foreground: var(--mui-palette-text-primary);
  --color-fd-muted:      var(--mui-palette-action-hover);
  --color-fd-border:     var(--mui-palette-divider);
}

The reason there is no second block for dark mode: MUI’s --mui-palette-* values are themselves redefined under its dark selector, so a single mapping at :root follows the app’s colour scheme for free. Fumadocs’ own .dark block becomes dead weight you can ignore. The docs then inherit your Roboto type stack, surfaces and borders, while keeping Fumadocs’ layout, sidebar behaviour and search UI — the parts you’d otherwise spend a sprint rebuilding.

The selector mismatch to know about

Your app and Fumadocs mark dark mode differently, and neither is wrong:

System Dark-mode marker on <html> Set by
Your app (MUI 9.3.1) data-dark InitColorSchemeScript attribute="data"
Fumadocs UI class="dark" next-themes, inside RootProvider

The shorthand is easy to get wrong: in @mui/system, colorSchemeSelector: 'data' expands to the rule [data-%s], so dark mode is the bare attribute data-dark — not data-mui-color-scheme="dark", which MUI uses only when you pass a full attribute name. The variable mapping above makes the mismatch a non-issue, because you never rely on Fumadocs’ .dark block at all.

Practical UI decisions

  • Keep your SiteHeader and SiteFooter. Fumadocs’ DocsLayout nests inside them. Add a Docs item to the existing nav so the site reads as one product with three areas, not two products sharing a domain.
  • MUI owns colour mode. It already has the working scheme system and the FOUC-preventing init script, so there is nothing for next-themes to add. Pass theme={{ enabled: false }} to Fumadocs’ RootProvider to switch it off entirely, and drive everything from MUI’s useColorScheme(). Running both is how you get a flash of the wrong theme on every docs page load.
  • Turn off the D hotkey with theme={{ hotKey: false }}. Fumadocs binds it to the dark-mode toggle by default. It is ignored while you type in an editable element, but your data grid has non-input interactive surfaces where it would still fire.
  • Reuse StatusChip’s colours as the docs’ semantic palette. Passed / tentative / cancelled already have a visual language in the app; callouts and rubric verdicts should speak it.
  • Target WCAG 2.1 AA, gated. Zero axe violations as a hard CI gate; Lighthouse accessibility at 100. A static docs site has no excuse, and unlike performance it isn’t flaky.
  • Content width around 68–72 characters. Fumadocs defaults wider than is comfortable for the long prose sections migrating out of the development guide.

10 Open decisions and risks

Decide before P1

  1. Where do the scraper docs live? This is the biggest unresolved question in the plan. The scraper building and QA docs describe code in city-scrapers-* repos, but would be published from meetings-viewer. That’s workable — and it’s the right call for a single readable site — but it means drift anchors (§7) point at code in other repos, requiring those repos checked out in CI. The alternative, docs living beside the code they describe, gives you N scattered doc sets and no unified search. Recommendation: keep one site here, accept cross-repo anchors, and start drift detection only on the viewer’s own docs.
  2. Who gets write access? Determines whether Keystatic is free or $10/month. Ask the mentors before assuming.
  3. Does /docs ship on the current production branch? The production branch is CS-116-landing-page-migration; confirm the branching plan so P1 doesn’t collide with it.
