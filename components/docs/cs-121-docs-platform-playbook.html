Building the rest of it

The original research got the platform decision right — Fumadocs inside the app is built and working. This playbook is what comes next: it keeps what's earned its place, cuts what the shipped app doesn't need yet, folds in the team's new City Scrapers Development Guidelines v1.1, and treats the reading experience — not the tooling checklist — as the actual deliverable. This revision closes the source set: five further documents — including the program-level Tech Guide owned outside CTD, a curated developer link list, and two agent skills — are now accounted for, and they force one genuinely new architectural decision (§1.5) and one correctness finding that reaches past this repo (§2.1).

Notation — planning only, never shipped

The § shorthand throughout this playbook is a drafting convention for cross-referencing source documents and this playbook's own sections. It must not survive into the built site: no § in any MDX page, heading, nav label, or component. Published pages name their source in prose ("per the Development Guidelines, Meeting schema") and link to headings by anchor. Section numbers also collide by coincidence between documents — where the source isn't obvious from the sentence, this playbook names the document explicitly.

Glossary

CTD = Code the Dream, the apprenticeship organization that builds and maintains the scrapers and this Meetings Viewer repo. PDW = Public Data Works, the partner engineering/design studio that operates Documenters.org and its data pipeline. CB = City Bureau, the partner org that runs the Documenters civic-journalism program and does editorial/data QA on scraper output. These three abbreviations recur throughout this playbook without re-expansion after this point.

Where this playbook disagrees with the original research

Four calls change, all in the direction of less new infrastructure and more use of what the app already has. Everything else in the original research — Fumadocs, MDX content, the built-in search route, llms.txt — stands and is already built.

01What changes, and why

Three items dropped on the first pass — added back here

A second check against the original research's §5 turned up three items this playbook's first draft silently lost instead of deliberately cutting. Deliberate cuts (Keystatic, the heavy CI roster, Fiberplane Drift, blanket Mermaid) are explained below. These three weren't cuts, they were oversights — fixed now, not re-argued:

  • §5.1's paste-JSON rubric-report tool — the original research called this "the highest-value page on the site." Restored as <RubricReport> in §4.2, P3.
  • Per-page .md routes and a copy-as-markdown button (§5.9) — Fumadocs ships both for free alongside the already-built llms.txt/llms-full.txt routes. Restored in §4.2 and P1.
  • Site-wide ⌘K search "reachable from anywhere, including from inside the viewer" (§5.10) — SiteHeader currently has no search trigger at all, so search is confined to /docs. Restored in §4.2 and P2.

1.1 Skip Keystatic — git and Docs are both already first-class

The original research treated GitHub-account editing as a limitation to work around. The Development Guidelines confirm apprentices are already required to fork, branch, open a draft PR, and carry it through a three-stage human review (§3.8–3.9 of the guide, and §3 of this playbook) — git literacy isn't incidental to the program, it's a large part of what it teaches. But the team writing this repo's own docs — the PM/ architect, the scraper developers, and the viewer developers — already has both git access to this repo and edit access to the source Google Docs those docs are drafted in. A WYSIWYG CMS would be solving an access problem nobody on that team actually has. Keystatic stays skipped, permanently, not just deferred (§9 still tracks it separately for PDW/CB, who genuinely lack both).

What replaces it isn't "git-only" either — it's git and Docs as two first-class, converging paths, resolved below.

The sync is an explicit allowlist, never "watch the whole doc"

The Docs sync maps specific document sections to specific target files — never "watch this whole doc, regenerate that whole folder." Two source documents, two different treatments:

  • Development Guidelines → /docs/scrapers, one-time seed only. This doc was never configured as an ongoing sync source. It seeded the P2 migration once, and from that point those pages are permanently git-owned — not because the doc might change, but because of the hard rule below. An unrelated edit anywhere else in that document must never be able to trigger a regeneration that deletes a live component.
  • Meetings Viewer Technical Spec → /docs/viewer/architecture.mdx, ongoing source. Unlike the Development Guidelines, this one maps to exactly one page, so it can stay wired as a live sync — right up until that page imports a component (§4.2's <SchemaTable> is a candidate, per §3, since the spec's own §4.1 data shapes overlap with qa/schema.mdx). The same hard rule applies the moment it does.

Ownership is by content type, not by author identity

CODEOWNERS assigns a reviewing pool per directory — it doesn't gate authorship. There's no single named "owner" to route around: anyone on the team may author a change through either path. The one hard, non-negotiable rule is technical, not political:

Any page importing a live app component is permanently git-owned

A Docs sync run regenerates the whole target file from the document and has no way to represent a component import — it would silently delete it. Three components already planned trigger this rule (§4.2): <SchemaTable> on qa/schema.mdx, <CommandBlock> across the scraper docs, and <RubricReport> on /qa. Once a page imports one of these, it never goes back to being a sync target — permanently, not until the next content review.

On any page that isn't component-locked, either path is open to anyone: edit the relevant Doc section and let the sync open the PR, or branch directly in git and open one yourself. Neither is gated behind the other. For a quick discovery worth documenting immediately — a new code pattern, a fix worth writing down before it's forgotten — go git-direct: fewer steps and lower latency than drafting in a Doc and waiting on the sync's next run and its conversion step. The Doc path is for prose someone would rather draft outside Markdown, not the default for speed.

A bidirectional conflict guard, not a silent overwrite

Before either mechanism writes a page, it checks whether the other path has moved since the last recorded sync point — a frontmatter marker carrying either the last-synced Doc revision ID or the last git-direct commit hash. If both moved, it fails open into a flagged PR for a human to reconcile, never a silent overwrite in either direction. This is the same discipline as §5's link checker: catch the collision in CI, don't let it ship as a surprise.

The citation stamp: date and source, never an author

Every page shows the reader "as of [date], per [source doc + version]" — never who opened the PR or wrote the edit. The date is never hand-typed:

  • Docs-synced pages pull it from the Google Drive API's modifiedTime/revision metadata at fetch time.
  • Git-owned pages use the last commit date on that file.
Verified, not assumed

The Development Guidelines .docx — a manual Google Docs export — contains no docProps/core.xml at all: not a blank author field, no metadata stream to hold one. unzip -l on the file confirms it. A manually exported .docx simply cannot be the source of a reliable date; the Drive API and git history are the only two sources this stamp is allowed to read from.

Nobody should ever be asked to hand-type a version line into a living internal doc just to keep this working — the moment a date is manually typed, it starts lying the first time someone forgets to update it, which is exactly the failure mode this whole playbook exists to design out.

Scope boundary

None of this changes anything for the Python scraper developers working in city-scrapers-core and consumer repos — they remain readers of /docs/scrapers and /docs/qa, in codebases this build has no visibility into. The payoff is internal: less duplicated maintenance and faster publishing for whoever on the CTD team is updating this repo's own docs.

1.2 Replace the tool roster with one build check

The failures this audit actually found were: a page linking to a section that doesn't exist, and a page claiming to be auto-generated when it's hand-typed. Vale, cspell, lychee, and Lighthouse CI solve problems this site doesn't have yet — prose style drift across many authors, external link rot, performance regressions on a content site that's currently five pages. Adopting five external tools to catch two internal-link bugs is the wrong trade for a five-page site maintained by a small team.

Ship next build plus a ~40-line internal link checker in CI instead (§5). Revisit the heavier roster once the site is large enough, or has enough outside contributors, that those specific failure modes start showing up for real.

1.3 Generate the one page that drifts, don't buy a drift detector

qa/schema.mdx already claims "this page is generated from [the TypeScript types] in lib/scrapers.ts." It isn't — it's hand-written, and per §2 below it's currently wrong in four places. Fiberplane Drift would eventually flag that this page and the code disagree; a generation script prevents them from ever being able to disagree, for the one page in the entire site where that risk is real. Build the generator (§5), keep the claim honest, and don't adopt fingerprinting tooling for a problem a small script already closes.

1.4 Match the diagram to the shape of the content

Not everything in the new guidelines is a graph. The five-stage PR review process (§3.9 of the guide) is a straight line — Draft → CTD review → Ready for review → Staging + CB QA → Sign-off. That's exactly what MUI's Stepper renders, and it's already a dependency — zero new packages, and it inherits the app's own visual system instead of Fumadocs importing a second one via Mermaid's theming. Reserve Mermaid (or hand-authored SVG, used below) for content that's actually a graph: the data-flow diagram in §3, and the two-workflow trust boundary behind the Airtable sync automation.

1.5 A third ownership class: mirrored external sources

§1.1's model has exactly two classes — git-owned and Docs-synced — and both assume the source is something this team can write to. The new source set breaks that assumption. The City Scraper Project Tech Guide and PDW's Overview of code review/QA issues are program-level documents owned outside CTD: nobody in §1.1's three-role scope can edit them, and neither lives in Google Docs, so the sync has nothing to attach to. Treating them as git-owned would quietly convert someone else's document into our copy, with no mechanism to notice when the original moves.

Class Source of truth Who writes Drift is caught by
Git-owned The MDX file itself Anyone with repo access, via PR Nothing needed — the file is the truth
Docs-synced An allowlisted Google Doc section PM/architect, scraper devs, viewer devs CI-3's bidirectional conflict guard
Mirrored NEW A document owned by another org Nobody here — we restate, we don't author CI-2 freshness TTL + a named human reviewer on the other team

Mirror or link? The deciding factor is machine-readability

The instinct is to link and be done — a link can't drift, which is §7's own rule. That instinct is right for most external material and wrong for this one case, for a reason worth stating precisely rather than as a preference:

Verified: the PDW review doc is not machine-readable

docs.pdw.co/city-scrapers-overview-of-reviews is a Craft-hosted single-page app. Fetching it returns a <div id="root">, a <noscript>, and nothing else — the content renders only after JavaScript executes. It also carries <meta name="robots" content="noindex">. That means: our link checker cannot validate it beyond a 200, our site search cannot index it, it has no stable heading anchors to deep-link, and — the point the team actually cares about — an agent reading our docs to give a developer feedback cannot read it either. A link to it is a dead end for every automated consumer this platform is being built to serve.

So: mirror the substance, link the source, and never pretend we own it. A mirrored page restates the review criteria in our own structure, carries a visible provenance line naming PDW and linking the original, and is explicitly not authoritative — where the two disagree, PDW's document wins and ours is the bug. Three rules keep that honest:

  • A named reviewer on the owning team, recorded in frontmatter. Not "PDW" as an abstraction — a person who agreed to be asked. Without one, the page doesn't ship; this is the concrete instance of §9's editing-authority question, and it blocks here rather than being deferred again.
  • A short ttl_days — 90, not the default. Mirrors of documents we can't watch decay faster than pages whose source we control. CI-2 already reads this field; a mirror just sets it lower.
  • Never mirror a page that imports a component. Same hard rule as §1.1, for the same reason: the mirror is refreshed by rewriting it.
Where the line falls

Mirror only what an automated consumer must be able to read: PDW's review criteria, and the Tech Guide's schema and scraper taxonomy. Everything else — the YouTube tutorials, Postman, the Scrapy and Legistar upstream docs, individual example spiders on GitHub — stays a link, because all of it is already public, stable, machine-readable, and owned by people who never agreed to be mirrored. §3's link registry is where those live.

2.1 The schema now has five descriptions, and they disagree

The new sources make a latent problem explicit. The meeting schema is now described independently in five places — the Development Guidelines (checked in the table above), the Tech Guide, both agent skills, and this site's own pages — while only one source is executable: constants.py in city-scrapers-core, the package every scraper repo imports. Everything else is prose about it. Checking the three new prose sources against that code found errors that have nothing to do with this repo — they are wrong at the program level, in the document new developers are onboarded with:

Fact city-scrapers-core (authoritative) Tech Guide PDW review skill Spider Development skill
Unclassified fallback NOT_CLASSIFIED = "Not classified" UNCLASSIFIED — no such constant Not listed NOT_CLASSIFIED — correct
Cancelled spelling CANCELLED = "cancelled" CANCELED — one L cancelled — correct CANCELLED — correct

The status row has teeth

PDW's review skill validates status against tentative, passed, cancelled — and that skill is meant to run as a GitHub Actions check on scraper PRs. A spider that correctly emits confirmed, a real constant in city-scrapers-core, would be flagged invalid by the automated reviewer. That isn't a documentation nit; it's a false positive in a check that gates other people's work.

What this justifies

Four independent prose copies of one enum, three already wrong, is a far stronger argument for §5's CI-4 generate-and-diff layer than this repo's Node-version pilot — and unlike that pilot, it affects every scraper repo. The fix is not "correct the four copies"; it's one generated table sourced from constants.py that the docs render and the skills cite. Hand-correcting the copies only resets the clock on the same drift.

Not ours to correct directly

The Tech Guide is a mirrored source under §1.5 — CTD doesn't own it. Report these to whoever maintains it rather than silently fixing them in our copy, and have our page render the generated table either way. That's the mirror contract working as designed: where mirror and source disagree the source wins; where source and code disagree the code wins and someone gets told.

03Information architecture, expanded

The Development Guidelines cover a lot the site doesn't have a home for yet: source analysis method, spider architecture patterns, bot-detection, testing, the full contribution and PR review workflow, and the CI/CD pipeline that runs scrapers in production. Some of that belongs under the existing two doors (§5.6 of the original research); some of it — the review process, the production pipeline — is neither "building" nor "reviewing" content, it's orientation content both audiences eventually need and a third kind of reader (a PM, a new CTD lead) may come to /docs looking for directly.

One structural risk the guide introduces: it describes a different repo family — city-scrapers-core and per-city consumer repos like city-scrapers-colgo — from the one this app's own /docs/contributing page describes (this Next.js repo). Blending them without saying so is exactly the kind of confusion this platform exists to prevent. Every new page that describes the scraper repos gets a repo-scope callout (§4).

The link list becomes a registry, not a page of links

The curated developer links — Scrapy and Python tutorials, the cityscrapers.org docs, the template repo, Postman, and the six worked spider examples chosen to illustrate one technique each — are genuinely valuable and currently live in a document nobody outside the team can find. Two rules keep them useful:

  • One registry file, many render points. Links live once in content/links.yml (URL, label, what it demonstrates, tags). /reference/links renders the full index; topic pages render a filtered slice — the six spider examples appear inline on scrapers/spider-patterns beside the pattern each one demonstrates, not only in a far-away list. Same one-input-many-outputs discipline as §5's CI-4, applied to links.
  • A registry is checkable; prose links are not. §1.2's build check validates internal links today. External ones pointing at .gov sites and pinned GitHub blobs are exactly the class that rots — and a registry gives CI one list to walk. This is the specific failure mode §5 deferred lychee against; when it shows up, the registry is already the shape lychee wants.
Two gaps to close while migrating, not after

The link list pins several examples to main rather than a commit SHA — those will drift silently as the referenced spiders are refactored; pin the SHA the way the Tech Guide already does for its examples. And the Tech Guide's "Starting a new city-scrapers repo" section is literally <Details to come>. Mirror it as a visible, dated gap rather than omitting it — a known hole someone can fill is worth more than a silent absence, and it's the single most useful page CTD could contribute back upstream.

Why a third top-level section instead of folding it into the two doors

§5.6 of the original research is still right that the homepage should force a two-way choice in the first three seconds — adding a third homepage option would blunt that. /pipeline isn't a third front door; it's reference material both existing doors occasionally link into (a QA reviewer wondering why staging behaves differently than production; a builder whose spider slug never shows up in Airtable), reached from the header nav and from in-context links, never competing with the homepage's choice.

The pipeline diagram missed a mode — corrected, then confirmed

This diagram's first draft said the Meetings Viewer "never touches production" and left it there. That was wrong in a way that matters, and the now-provided Meetings Viewer Technical Specification confirms it precisely (§6, its own "Production mode (not yet fully planned)"): a second, planned mode fetches PR-scoped scraper output from a dedicated public meetings-viewer-data repo, laid out as prs/{scraper_repo}/{pr_number}/manifest.json plus a scrapers/ subfolder — populated by two workflows living in each scraper repo: run-and-save.yml (runs on PR open/update, commits output) and cleanup-data.yml (runs on PR close, deletes that PR's directory regardless of merge state). The viewer reads it via plain raw.githubusercontent.com URLs under a /pr/{repo}/{pr_number}/scrapers route — no backend, no database, no auth on the read side (§7's architectural invariants are explicit about this). Same UI, same components, same routes as local mode — only lib/scrapers.ts's implementation changes (§5.2). That mode doesn't touch Documenters.org's Azure/ETL/Postgres pipeline either, but it's explicitly meant to be used during PR review — which means by PDW and CB, not just by a CTD apprentice at their own keyboard. Does this actually reach PDW, CB, and everyone past this repo?

The content scope does, now — the Development Guidelines integration means /docs describes CTD, PDW, and CB's roles in the review pipeline (§3.9) and the production infrastructure none of them individually owns. 05Automation, the lean version

Right now there is no CI for the docs at all — no .github/workflows in this repo. Four small, deterministic workflows close the actual gaps found in this audit and enforce §1.1's sync model; everything heavier from the original research's tool table is deliberately deferred (§1.2). None of them cost money — every check below runs on facts already in the repo or free API calls, never a paid step.

CI-1

docs-build.yml

On any PR touching content/docs/** or components/docs/**: run next build (catches broken MDX and bad imports) and a ~40-line link checker that walks source.getPages() and confirms every /docs/... link and #anchor in the content resolves against real pages and headings. This is the check that would have caught the dead #drift-detection link in §2 before it shipped.

CI-2

docs-freshness-score.yml

Upgraded from a single regenerate-and-diff check into a composite score per page, computed in CI, fully deterministic:

  • Git-age delta — days since the page's last commit vs. days since the source-of-truth it cites last changed (the Doc's modifiedTime, or the code symbol's last commit, per §1.1's citation stamp).
  • TTL — a per-page ttl_days frontmatter value (kept from the original research's P5); expired pages flag even with no upstream change, since some content ages out on its own (a schedule reference, a version number).
  • Symbol-existence check — for pages naming a specific code symbol (a type, a field, a function), confirm it still exists at the cited path. A renamed or removed symbol fails the check immediately, before any age threshold is reached.

For <SchemaTable> specifically, this subsumes the old regenerate-and-diff idea: run the generator, fail if git diff is non-empty. The composite score generalizes it to every page with a citation stamp, not just the one generated page.

Mirrored pages (§1.5) lean entirely on the TTL leg. Their source is a document this repo can't watch — no modifiedTime, no commit history, no symbol to check — so the age delta and symbol checks have nothing to read. That's the whole reason the mirror contract sets ttl_days: 90 rather than the default: on a mirrored page the TTL isn't a backstop, it's the only signal there is, and its expiry means "go ask the named reviewer whether this still matches," not "this is stale."

CI-3

docs-sync-conflict-guard.yml

Implements §1.1's bidirectional guard: before the Docs sync writes a page, or a git-direct PR touches one still on the allowlist, compare the page's frontmatter marker (last-synced Doc revision, or last git-direct commit hash) against both sources' current state. Either side having moved past that marker is fine; both having moved is a conflict — fail open into a flagged PR with both diffs attached, never an automatic merge in either direction.

CI-4

docs-facts-regenerate-check.yml

One input-source layer for this repo's own code-native facts (schema fields, Node version, mode-status flags), feeding README.md, the landing page, and the relevant docs pages. Live import for code consumers — exactly what <SchemaTable> already does. For places that can't import a component (static prose like README.md): generate the value and fail if git diff is non-empty, the same pattern as CI-2, scoped to facts instead of a whole page.

Pilot case, already found

README.md line 39 says Node.js 18.18+. package.json's engines field says >=20.9.0. Two hand-maintained copies of the same fact, already disagreeing. Validate this layer against fixing that one pair first — a single generated line sourced from package.json's own engines field — before expanding to schema fields (already covered by <SchemaTable>) and mode-status flags (README's "(planned)" on Production mode, currently typed in two places by hand).

Second input, higher stakes: the schema constants

§2.1 found the same failure mode with far more reach — one enum, four prose copies, three of them wrong, in documents that onboard developers and gate PRs across every scraper repo. Add city-scrapers-core's constants.py as a second input to this layer: fetch it at build time, pinned to a release tag, and generate the classification and status tables that <SchemaTable> renders. Fail the build if the pinned tag's constants no longer match what the site publishes.

It's a cross-repo fetch, which the rest of this playbook deliberately avoids — the justification is that this is the one fact the docs assert that other teams' automation already acts on. Pin the tag rather than tracking main, so an upstream change surfaces as a deliberate bump in a PR, not as a silent shift under a page nobody re-read.

Explicitly deferred, not rejected

Vale + cspell, a lychee link-rot crawl, axe-core + Lighthouse CI, and Fiberplane Drift all remain reasonable additions — later. Revisit each once its specific failure mode actually shows up (prose drift across many authors, external .gov link rot, a11y regressions, code-vs-docs drift outside what CI-2/CI-4 already cover), not on a fixed schedule.

Correction — this is by design, not unfinished

07Agents, memory & skills

A new category, deliberately started thin: a shared place for how teams use AI coding agents effectively — not just CTD, but the frontend team on this repo, whoever owns the scraper repos, whoever owns the CI/CD automation in §3's /pipeline, and any team that comes after. The goal is the same one behind everything else in this playbook: less duplicated tribal knowledge, less onboarding by osmosis. The difference here is that almost none of the content exists yet — so this section is a method for growing it team by team, not a finished IA to fill in.

Where this repo actually stands today

One file: AGENTS.md, one rule (a warning that this app's pinned Next.js version has breaking changes versus a model's training data). No .claude/skills/, no .claude/agents/, no hooks. That's the honest starting point — nothing below invents practices this repo doesn't have yet.

The vocabulary — four mechanisms, one job each

Mechanism Lives at For In this repo, today
Memory AGENTS.md / CLAUDE.md, repo root Standing context every agent session in this repo loads automatically — the guardrails you'd otherwise repeat in every prompt One rule (above)
Skill .claude/skills/<name>/SKILL.md A packaged, reusable procedure — a checklist or workflow invoked by name mid-session, not repeated from memory each time None yet
Subagent .claude/agents/<name>.md A specialized persona with its own tool access, for a recurring task worth a dedicated role — a reviewer, a researcher None yet
Hook .claude/settings.json An automated action on a session event — run a formatter after every edit, block a risky command None yet

The decision method is short: something every session must always know → memory. A procedure you'd explain the same way every time → a skill. A distinct role worth its own context and tool scope → a subagent. Something that should happen automatically, unasked → a hook. Most teams starting out will only ever need the first two.

The method: how a team adds its own section

  1. Write down one real thing, not a speculative one. The smallest actual convention your team already applies with an agent — not an aspirational list of everything a well-run team's agent setup could someday include. This playbook's own rule against building for hypothetical readers (§1) applies here too.
  2. The real file lives in your team's own repo, not here. An agent session working in city-scrapers-core only ever reads that repo's AGENTS.md and .claude/ directory — nothing hosted only in city-scrapers-meetings-viewer's docs is ever loaded by a session working elsewhere. Put the actual memory/skill/agent/hook file where it will actually be read.
  3. This site links to it and summarizes intent in two or three sentences — never a copy. Same reasoning as §1.3: a duplicate goes stale the moment the source changes and nobody notices. A link can't drift out of sync with itself.
  4. List it on /docs/agents's team table and open a PR the same way your team reviews anything else.
Lighter governance than §3's PDW/CB content — with one exception

§9 raises a real open question about who can correct content describing PDW/CB's own process, because they don't have git access to this repo. For most of this section that doesn't apply: every team it's written for — scrapers, this app's frontend team, whoever owns CI/CD — already has git access to their own repo, and the only discipline needed is link-not-duplicate, above.

The exception is §7.1's code-review skill, which PDW owns. The page describes it and links to it; it must not restate its checklist or imply CTD maintains it. Link plus a two-sentence summary of intent — step 3 of the method above — is the whole treatment, and it keeps this page out of §9's editing-authority problem rather than adding a second instance of it.

7.1 Two skills already exist — the stub was wrong

The tree below listed scrapers.mdx as a stub owned by another team. That's now out of date: two real skills exist, they're already in use, and together they cover both ends of the scraper lifecycle. This becomes the section's most substantial page rather than its emptiest.

Spider Development skill Code-review skill
Owner CTD PDW
When it fires While writing a spider — build, refactor, debug After the PR opens — standalone or a GitHub Actions check
Shape Prescriptive: seven spider types with code, required standards, API patterns (CivicClerk, Legistar, Diligent, Drupal), anti-blocking recipes Evaluative: review mindset, a process, a large reference checklist, output-validation tables

Two skills at two lifecycle stages is a genuinely good split, and worth documenting as the recommended shape for any team that adds its own: one skill that helps you write it, one that checks what you wrote, and no overlap between them. That's the reusable lesson /agents exists to carry.

Defect, worth fixing before this page cites it

The Spider Development skill's frontmatter still carries the template placeholder: description: A brief description, shown to the model to help it understand when to use this skill. Paired with trigger: model_decision, the description is the only signal the model has for when to load it — so as written, it either never fires when it should or fires when it shouldn't. The skill's own body has the real description in its first line ("Use this skill when building, refactoring, or debugging Scrapy spiders for city-scrapers projects"); it just needs to move up into the frontmatter. One-line fix, and it's the difference between a skill that works and one that's installed but inert.

Skills cite the docs; they don't restate them

Both skills currently carry their own copies of facts the docs also publish — the meeting schema, the status and classification constants, the lint and test commands, the validation checklist. §2.1 is what that costs: the copies have already drifted from constants.py, and one of them will fail a correct spider in CI. The rule that prevents a repeat is the mirror of §7's link-not-duplicate rule, pointed the other way:

The docs hold the facts; the skills hold the judgment

A skill should carry procedure, heuristics, and worked examples — the things that are genuinely its own. For anything enumerable and generated (schema fields, constants, commands, the QA rubric) it should link to the doc anchor instead of restating it. That's only workable because the site publishes per-page .md routes and llms-full.txt (§4.2): an agent can follow the link and read the canonical text directly. This is the concrete answer to "we want agents reading our docs to give developers feedback" — the docs stop being a copy of the skill and become the thing the skill defers to.

Two consequences worth building for. First, <RubricReport> (§4.2) and PDW's review checklist are validating the same output against the same rules — both should read §5's generated constants, so a fix in city-scrapers-core reaches the interactive checker and the CI reviewer at once. Second, treat agent-readability as a page requirement rather than a nice-to-have: a mirrored page whose whole justification is that agents can't read the original (§1.5) has to be reachable as clean Markdown, or it inherits the defect it was created to fix.

What ships now vs. what's a stub

/docs/agents index.mdx — the vocabulary, the decision method, the team table how-to-add-a-section.mdx — the four-step method above, as a copy-pasteable checklist meetings-viewer.mdx — ships now: this repo's one real rule, honestly, plus what to add next scrapers.mdx FIX — ships now, not a stub: the two-skill lifecycle split, both skills linked, the docs-hold-the-facts rule (§7.1) devops.mdx — stub: "owned by whoever maintains the CI/CD in /pipeline — not written yet" + one page per team, added as each team runs the method above

meetings-viewer.mdx's "what to add next" isn't a guess — this playbook already wrote the candidate content in §4.3's standing rules (repo-scope callouts, commands copy-pasteable as written, dark-mode parity before merge). That's a real skill's worth of material sitting right there, unpackaged.

  • Which tool actually runs the Docs sync (§1.1)? This playbook specifies required behavior — explicit per-section allowlist, Drive API metadata for the citation stamp, a frontmatter conflict marker — not an implementation. Options span a custom Apps Script + Drive API webhook + GitHub Action, to an existing Docs-to-Markdown sync tool adapted to the allowlist and conflict-guard requirements. Resolve this as part of P1.5 — content authoring in P2 shouldn't start against a mechanism that's still notional.
  • Is a cross-repo fetch acceptable for the constants (§5)? §2.1 makes the case that constants.py should be a build-time input, pinned to a release tag. That's the one dependency this playbook otherwise avoids — the docs build would fail if an upstream repo were unreachable. The alternative is vendoring the constants with a CI check that compares them against upstream weekly, which trades build fragility for a slower feedback loop. Pick one deliberately in P1.5; both are defensible, and doing neither means keeping the four drifting copies §2.1 found.
