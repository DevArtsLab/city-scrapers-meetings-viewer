Building the rest of it

The original research got the platform decision right — Fumadocs inside the app is built and working. This playbook is what comes next: it keeps what's earned its place, cuts what the shipped app doesn't need yet, folds in the team's new City Scrapers Development Guidelines v1.1, and treats the reading experience — not the tooling checklist — as the actual deliverable.

Where this playbook disagrees with the original research

Four calls change, all in the direction of less new infrastructure and more use of what the app already has. Everything else in the original research — Fumadocs, MDX content, the built-in search route, llms.txt — stands and is already built.

01What changes, and why

Three items dropped on the first pass — added back here

A second check against the original research's §5 turned up three items this playbook's first draft silently lost instead of deliberately cutting. Deliberate cuts (Keystatic, the heavy CI roster, Fiberplane Drift, blanket Mermaid) are explained below. These three weren't cuts, they were oversights — fixed now, not re-argued:

  • §5.1's paste-JSON rubric-report tool — the original research called this "the highest-value page on the site." Restored as <RubricReport> in §4.2, P3.
  • Per-page .md routes and a copy-as-markdown button (§5.9) — Fumadocs ships both for free alongside the already-built llms.txt/llms-full.txt routes. Restored in §4.2 and P1.
  • Site-wide ⌘K search "reachable from anywhere, including from inside the viewer" (§5.10) — SiteHeader currently has no search trigger at all, so search is confined to /docs. Restored in §4.2 and P2.

1.1 Skip Keystatic — the git path is the point

The original research treated GitHub-account editing as a limitation to work around. The new Development Guidelines say otherwise: apprentices are already required to fork, branch, open a draft PR, and carry it through a three-stage human review (§3.8–3.9 of the guide, and §3 of this playbook). Git literacy isn't incidental to the program — it's a large part of what it teaches. Standing up a second CMS surface with its own auth and content model to spare editors that exact workflow works against the thing the org is optimizing for.

Keep the git path as the only path through at least P4. If a specific non-engineer editor is later named who genuinely can't use github.dev (already documented in contributing/index.mdx as the stopgap), revisit Keystatic then — as a scoped answer to a real person, not a default.

1.2 Replace the tool roster with one build check

The failures this audit actually found were: a page linking to a section that doesn't exist, and a page claiming to be auto-generated when it's hand-typed. Vale, cspell, lychee, and Lighthouse CI solve problems this site doesn't have yet — prose style drift across many authors, external link rot, performance regressions on a content site that's currently five pages. Adopting five external tools to catch two internal-link bugs is the wrong trade for a five-page site maintained by a small team.

Ship next build plus a ~40-line internal link checker in CI instead (§5). Revisit the heavier roster once the site is large enough, or has enough outside contributors, that those specific failure modes start showing up for real.

1.3 Generate the one page that drifts, don't buy a drift detector

qa/schema.mdx already claims "this page is generated from [the TypeScript types] in lib/scrapers.ts." It isn't — it's hand-written, and per §2 below it's currently wrong in four places. Fiberplane Drift would eventually flag that this page and the code disagree; a generation script prevents them from ever being able to disagree, for the one page in the entire site where that risk is real. Build the generator (§5), keep the claim honest, and don't adopt fingerprinting tooling for a problem a small script already closes.

1.4 Match the diagram to the shape of the content

Not everything in the new guidelines is a graph. The five-stage PR review process (§3.9 of the guide) is a straight line — Draft → CTD review → Ready for review → Staging + CB QA → Sign-off. That's exactly what MUI's Stepper renders, and it's already a dependency — zero new packages, and it inherits the app's own visual system instead of Fumadocs importing a second one via Mermaid's theming. Reserve Mermaid (or hand-authored SVG, used below) for content that's actually a graph: the data-flow diagram in §3, and the two-workflow trust boundary behind the Airtable sync automation.

02Fix the record before adding anything

The Development Guidelines v1.1 is the authoritative source for the Meeting schema — it's the document CTD reviewers actually QA against. Cross-checking it against what's live on /docs today turned up four factual errors, one dead cross-reference, and confirmed the fabricated "generated" claim from §1.3. All four schema errors were verified against a real fixture, not just the guide's prose:

Verified against data/scrapers/test_spider1.json

"start": "2024-06-17 13:00:00" — no T, no offset, no Z. The app's own MeetingRecord type (lib/scrapers.ts) types start/end as a bare string and every component renders it as-is, unparsed. The live docs' claim of a timezone-aware ISO 8601 string doesn't match the data the app actually ships with.

Resolved, not just observed

Confirmed with the team: this is by design, not a bug to fix. The viewer is meant to show exactly what the spider produced — no client-side parsing, no normalization, no reformatting. Document that as a stated principle on qa/schema.mdx itself (§3), not just fix the tz-naive wording — it's the answer to why the field renders as a raw string at all, and it forecloses a future "helpfully" reformat-on-read PR that would make the viewer stop matching its own source of truth.

03Information architecture, expanded

The Development Guidelines cover a lot the site doesn't have a home for yet: source analysis method, spider architecture patterns, bot-detection, testing, the full contribution and PR review workflow, and the CI/CD pipeline that runs scrapers in production. Some of that belongs under the existing two doors (§5.6 of the original research); some of it — the review process, the production pipeline — is neither "building" nor "reviewing" content, it's orientation content both audiences eventually need and a third kind of reader (a PM, a new CTD lead) may come to /docs looking for directly.

One structural risk the guide introduces: it describes a different repo family — city-scrapers-core and per-city consumer repos like city-scrapers-colgo — from the one this app's own /docs/contributing page describes (this Next.js repo). Blending them without saying so is exactly the kind of confusion this platform exists to prevent. Every new page that describes the scraper repos gets a repo-scope callout (§4).

Why a third top-level section instead of folding it into the two doors

§5.6 of the original research is still right that the homepage should force a two-way choice in the first three seconds — adding a third homepage option would blunt that. /pipeline isn't a third front door; it's reference material both existing doors occasionally link into (a QA reviewer wondering why staging behaves differently than production; a builder whose spider slug never shows up in Airtable), reached from the header nav and from in-context links, never competing with the homepage's choice.

The pipeline diagram has to say what the Meetings Viewer isn't

The clearest gap the new guide exposes: nothing on the current site explains that this app is a local, dev-time QA tool reading a spider's local -O output — not a stage in the production path that actually serves Documenters.org. Without that line, a new contributor could reasonably assume this app is part of the pipeline in §4.1. The diagram below is the fix — production and local-QA are drawn as two separate paths from the same source, joined only at "a person reads the JSON."

The Meetings Viewer never touches Azure, the ETL job, or Postgres — it reads whatever JSON is sitting in data/scrapers/ on your machine. This is the single most important thing /docs/pipeline has to make obvious.

04UX / UI system for the content

This is the part the original research under-weighted and this playbook doesn't: the platform choice and the CI checklist are both in service of pages people actually want to read. Two things need to happen before the new content lands — one fix, one small component set — plus a few standing rules for every page after.

4.1 Ship the theme mapping that was always the plan

globals.css currently only imports Fumadocs' stock neutral.css preset — none of the --color-fd-* → --mui-palette-* mapping from the original research's §8 was ever added. Dark mode switching works (DarkModeSync correctly drives Fumadocs' .dark class off MUI's color scheme), but /docs is still rendering in Fumadocs' generic gray, not the app's own palette. This is a five-variable, one-time fix with no new dependency — do it before any of the new pages ship, so every page that follows is on-brand from day one instead of needing a re-skin later.

What that stepper should look like on /qa/review-process — five stages, each naming who's involved and what "done" looks like, replacing the guide's prose walkthrough of §3.9:

1

Draft

Contributor opens the PR as a draft once the spider is ready for a first pass.

2

CTD review

Team lead QAs output against §2.5 and reviews code — logic, style, edge cases, tests.

3

Ready for review

Feedback addressed; PDW reviewers added; Airtable backlog moved to staging-ready.

4

Staging + CB QA

PDW merges to staging; City Bureau QAs the live output; PR stays open for fixes.

5

Sign-off

CB signs off in Airtable; PR merges to main; the scraper goes live.

4.3 Standing rules for every page from here on

  • One repo-scope callout on any page describing the scraper repos, placed above the fold — never assume the reader knows which codebase a command runs against.
  • Commands are copy-pasteable as written. The guide is precise about flags that matter (-O not -o, pipenv run prefixes) — docs must never round that off for brevity, since the flag itself is the QA lesson.
  • Good/bad example pairs (already used well for title formatting) become a recurring pattern, not a one-off — it's the exact shape a reviewer scans for.
  • Dark mode + MUI parity checked before merge on every new docs page — keep this as a standing PR habit, not a one-time P0 spike item.

05Automation, the lean version

Right now there is no CI for the docs at all — no .github/workflows in this repo. Two small workflows close the actual gaps found in this audit; everything heavier from the original research's tool table is deliberately deferred (§1.2).

CI-1

docs-build.yml

On any PR touching content/docs/** or components/docs/**: run next build (catches broken MDX and bad imports) and a ~40-line link checker that walks source.getPages() and confirms every /docs/... link and #anchor in the content resolves against real pages and headings. This is the check that would have caught the dead #drift-detection link in §2 before it shipped.

CI-2

docs-generate-check.yml

Once <SchemaTable>'s generator (§4.2) exists: run it and fail the build if git diff is non-empty. This is the original research's P5 "regenerate-and-diff" idea, scoped to the one page that actually needs it instead of a platform-wide drift product.

Explicitly deferred, not rejected

Vale + cspell, a lychee link-rot crawl, axe-core + Lighthouse CI, and Fiberplane Drift all remain reasonable additions — later. Revisit each once its specific failure mode actually shows up (prose drift across many authors, external .gov link rot, a11y regressions, code-vs-docs drift outside the one generated page), not on a fixed schedule.

06Fleet & performance, for senior developers

Everything so far serves two readers: someone building a spider, someone reviewing one. Neither view answers a question a team lead actually has — across every spider this cohort has shipped, what's healthy, what's stale, and is the docs platform itself fast? That's a third audience, and it's a different job: fleet-wide visibility, not single-spider QA.

This isn't invented — it's half-built already

components/scrapers/ScrapersTable.tsx already defines Status and Last Run columns (fields last_run_status and last_run) on the spider list. lib/scrapers.ts's SpiderEntry type declares both fields. But listScrapers() only ever returns {"{"} slug {"}"} — agency, last_run, and last_run_status are never populated, so every row renders the — placeholder permanently. The table was built for fleet visibility and never finished.

Keep it local, the same way the rest of the app already is

§3's diagram established that this app is a local, dev-time tool — it never talks to Azure, the ETL job, or Postgres. Fleet data should hold that same line rather than reaching for the real Airtable spider registry from client code:

  • Local signal, computed from what's already on disk. File mtime on each data/scrapers/<slug>.json stands in for last_run; a schema self-check — reusing <RubricReport>'s validation from §4.2 — stands in for last_run_status (healthy / stale / schema-errors). This finishes SpiderEntry honestly with zero new integrations.
  • The real Airtable-backed version is a separate, bigger decision — see §8. The Airtable PAT is a write-scoped org secret (per the guide's §4.3); it can never reach client-side code in this Next.js app. A live version needs a server-only Route Handler and its own security review, not a quick client fetch.

The other half: is the docs platform itself fast?

§1.2 deferred axe-core + Lighthouse CI for having no place to show results. This tab is that place — the condition is now met, so it's back on the roadmap (§7, P7), scoped tightly: Lighthouse CI writes one JSON artifact per build; this page renders it. No new runtime dependency, no telemetry service, nothing that phones out from a user's browser.

08Open decisions for the team

Closed

Raw-string rendering, no normalization, ever. The viewer shows exactly what the spider produced — confirmed with the team (§2). Not an open question anymore; a stated principle to write into qa/schema.mdx.

  • Who owns /pipeline content? It describes CTD/PDW/CB process and production infrastructure — confirm it's fine to keep in an OSS-visible docs site before writing it, rather than after.
  • Source-of-truth risk for the CI/CD pages. The Airtable sync and cron-workflow content describes city-scrapers-core's actual automation. If that repo's workflows change, this copy goes stale silently — the exact failure mode this whole platform exists to prevent. Consider a last_reviewed callout on those three pages specifically, even before the general freshness-tracking idea from the original research's P5 exists anywhere else.
  • Keystatic: closed unless someone is named. Per §1.1, don't keep this as a recurring "should we" question — treat it as decided until a specific non-engineer editor needs it.
  • Local fleet signal vs. a live Airtable-backed one (§6). The local version (file mtime + schema self-check) ships in P7 with zero new integrations. A version backed by the real spider registry is materially bigger scope — a server-only Route Handler, a read-scoped Airtable token held as a Vercel environment variable, and its own security review before any senior developer sees real fleet data in this app. Decide explicitly before P7 drifts into building it; don't let it happen by accident because "the API's right there."
